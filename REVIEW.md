# REVIEW.md

These are the bugs I found in the starter file `app/main.py`. I fixed all of them in my submitted file.
"R#" means the business rules written in `openapi.yaml`.

| # | Where | What is wrong | How you can see the bug | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | The shift start was made from the UTC time, so the shift time was compared in UTC and not in IST (R1). | Shift 09:30, punch-in 10:05 IST (04:35Z). The start became 09:30Z, so the difference was negative and `late_minutes` was 0 instead of 35. Every late punch looked on time. | I now build the shift start as an IST time for the attendance date (`at_ist`). |
| 2 | `compute_late_minutes` | The code rounded down to minutes first and then checked `minutes > 10`. R2 says "strictly more than 10:00". | 09:40:01 on a 09:30 shift: rounding down gives 10, and `10 > 10` is false, so the answer was 0 instead of 10. | I compare whole seconds (`> 600`) first, then convert to minutes. |
| 3 | `compute_late_minutes`, `punch_in` | Night shifts were not handled, and seconds were not cut to whole numbers. | Shift 22:00-06:00, punch-in 01:00 IST belongs to the previous day's shift (R1) but was measured against the wrong day. Punch-in `09:40:00.900` was treated as 09:40:00.9. | `attendance_date()` applies the R1 night shift rule. `ms_to_dt()` removes the fractional seconds before any calculation. |
| 4 | `compute_work_hours` | Python's `round()` on a float uses banker's rounding and has float errors. R4 wants normal half-up rounding. | 450 seconds = 0.125 h. `round(0.125, 2)` gives 0.12, but 0.13 is expected. | I use exact `Decimal` math with `ROUND_HALF_UP`. |
| 5 | `compute_overtime` | `max(0, minutes)` ignores the 30-minute minimum (R3). The shift end was always on the attendance date, so night shifts were wrong. | Shift end 18:30, punch-out 18:45: the code returned 15 but 0 is expected. For a 22:00-06:00 shift the value was negative and was changed to 0. | It returns minutes only when they are `>= 30`. For night shifts the shift end is on the next day. |
| 6 | `compute_overtime` + client | `MongoClient` returns datetimes without timezone (naive). The function subtracted a naive datetime from an aware one. | Punching out on a record read from MongoDB raised `TypeError`, which became a 500 error. | I use `MongoClient(tz_aware=True)`. Everything is aware UTC, and IST is used only for the rules and calendar dates. |
| 7 | `punch_in` | `datetime.fromtimestamp(ms/1000)` and `datetime.now()` use the server's local timezone, and `ts.date()` is not the IST date (R1). Dividing as float also loses precision. | Server in UTC, punch-in at 00:30 IST: the record got the previous day's date. | I convert with `ms // 1000` in UTC and calculate the date in IST using `attendance_date()`. |
| 8 | `punch_in` | `emp` can be `None` (employee does not exist), so `emp["shift_start"]` raises `TypeError`. | `POST /attendance/punch-in {"emp_code":"NOPE"}` returned 500, but 404 is expected. | `get_employee()` now raises 404. |
| 9 | `punch_in`, `create_employee` | The code did "check, then insert" (`find_one` then `insert_one`). This has a race condition, and there was no unique index. | Two parallel punch-ins (or two parallel creates) both got 201 and a duplicate document was saved. | I create unique indexes on `(emp_code, date)` and `emp_code` at startup. The insert is the only check, and `DuplicateKeyError` becomes 409. |
| 10 | `PunchInIn`, `EmployeeIn` | The models accepted anything. `status: str` accepted `"FOO"` or `"ABSENT"`. `punched_at` accepted floats, numeric strings and values in seconds. Employee fields had no format checks. | `emp_code:"abc"`, `email:"x"`, `shift_start:"25:99"`, `shift_start == shift_end` and `joined_on:"2026-02-30"` were all saved. | I use strict types, patterns and `Literal` for status. `EpochMs` is a strict int in `[1e11, 4.1e12]`. Validators check dates and `shift_start != shift_end`. Invalid input gives 422. |
| 11 | `punch_in`, `create_employee`, `list_attendance` | Responses leaked `_id` as `id` and returned datetimes (ISO strings) where the contract wants epoch milliseconds. `created_at` was saved as naive local time. | The `punch_in` response had an `id` field and `"punch_in": "2026-07-06T10:05:03"`. | `employee_out()` and `record_out()` build the response shape by hand: no `_id`, times as epoch ms, and `created_at` saved as UTC. |
| 12 | `list_employees` | `skip = page * page_size` is off by one, so page 1 skipped the first page. `page=0` or negative gave a negative skip (500 from MongoDB), and `page_size` had no limit. | `GET /employees` never returned the first 20 employees. | `skip = (page - 1) * page_size`, with `page >= 1` and `1 <= page_size <= 100` (otherwise 422). |
| 13 | `list_employees` | `total` counted the whole collection, not the filtered result (R10). There was no sort, so pages were not stable. | `?department=Eng` returned 3 items but `total` showed all employees. | I use `count_documents(q)` with the same filter, and `sort("emp_code")`. |
| 14 | `list_attendance` | It loaded the whole collection into memory and sorted and sliced in Python. There was no index. Sorting was by `date` only, with no `emp_code` tie-break. | With 100k records, every call read 100k documents. Order inside the same date was random. | MongoDB now does `find().sort(date desc, emp_code asc).skip().limit()` using an index, and `count_documents` gives `total`. |
| 15 | `list_attendance` | No validation for dates, status, page or page_size. `date_from > date_to` was accepted. Old documents without `half_day` or `history` broke the response. | `?date_from=2026-13-01`, `?page=0` and `?status=BAD` were accepted. Page 0 sliced from `-20`. | Dates are parsed and checked (422), `status` is a `Literal`, and paging has limits. `record_out()` gives defaults for missing fields (`half_day` false, `history` empty, minutes 0). |
| 16 | `/health` | It always returned OK, even when MongoDB was down. | Stop MongoDB: `/health` still returned 200. | It now pings MongoDB and returns 503 on failure. `serverSelectionTimeoutMS=5000` makes it fail fast. |
| 17 | startup | No indexes were created (the grader's database has only `_id`). | Slow list and analytics queries, and no uniqueness protection. | `ensure_indexes()` runs at startup, and again from `/health` if it failed. It is safe to run many times and thread-safe. |

## Things I checked and decided were fine

- `load_dotenv()` does not override variables that are already set, so real environment variables win, as the contract requires. I kept it.
- The default `mongodb://localhost:27017` / `attendance_db` is only a fallback for local development. The grader sets `MONGO_URI` and `MONGO_DB`.
- The starting values written at punch-in (`punch_out: None`, `work_hours: None`, `overtime_minutes: 0`, `half_day: False`, `history: []`) match DATA_MODEL.md.
- The `{"_id": 0}` projection in `list_employees` is correct. The problem was the response shape in the other endpoints.
- I kept the helper function names and purpose, but rewrote their bodies, because they could not be reused as they were (bugs 1 to 6).
